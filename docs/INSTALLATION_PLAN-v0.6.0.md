## How to use this plan

- Work from top to bottom unless a task records a blocker.
- Check an item only after its acceptance criteria have been met.
- Add the commit, test output, workflow run, or manual result to the evidence
  log before calling a workstream complete.
- Update **Current handoff** at the end of every session, even when the work is
  incomplete.
- Keep paid Apple and Microsoft certificates out of the v0.6.0 critical path.
  Windows and macOS are deferred entirely; their absence must not affect the
  Linux-only release.
- Do not commit or push unless the user explicitly requests it.

## Release policy for v0.6.0

### Supported

- **Linux x86_64:** `.deb` for Debian/Ubuntu and AppImage for portable use.

### Deferred

- **Windows x86_64** and **Apple Silicon macOS** are held for a later release.
  No v0.6.0 packages, native verification, or signing work is required for
  these platforms.

### Not offered in v0.6.0

- Windows, macOS, Intel macOS, AUR, Flatpak/Flathub, and Homebrew.
- Claims that deferred Windows or macOS packages are available in v0.6.0.

The Tauri updater signature is separate from Windows Authenticode and Apple
code signing. Updater signing remains mandatory wherever automatic updates are
advertised; it does not remove SmartScreen or Gatekeeper warnings.

## Definition of done

v0.6.0 is ready when:

- [ ] A visitor can identify the correct artifact and install it without
      interpreting release filenames.
- [ ] Provider credentials survive an application restart on Linux using the
      native Secret Service credential store.
- [ ] Release automation behaves successfully without paid OS-signing secrets
      and publishes only the Linux artifact set.
- [ ] Every published platform and architecture has an accurate support label,
      installation procedure, limitation list, and update policy. v0.6.0
      publishes Linux x86_64 only.
- [ ] Published Linux packages are installed and launched in a clean
      environment.
- [ ] The release page contains human-readable download guidance and known
      limitations, not only an autogenerated changelog link.
- [ ] Dead distribution paths and false claims are removed or explicitly
      deferred.
- [ ] The release workflow and required CI checks are green, apart from a
      clearly recorded external infrastructure blocker accepted by the user.

## Workstream 1 — Native credential persistence

**Done when:** saving a provider key uses the real native credential store and
the key is available after the application is fully stopped and restarted.

- [x] Replace the global Linux-only `keyring` feature with a persistent Linux
      Secret Service/native backend and document its restart behavior. Windows
      and macOS target backends remain deferred with their platforms.
- [x] Prevent a production build from silently using keyring's mock backend.
      Target backend modules are referenced directly, so a missing native
      feature fails compilation; runtime persistence detection also maps the
      mock backend to `memory`.
- [x] Make `KeyStorage` report what actually happened; a mock/in-memory write
      must never be reported to the UI as `keyring`. A process-memory fallback
      keeps the key usable until restart without writing it to disk.
- [x] Add focused tests for backend selection and key-storage status.
- [ ] Compile the Linux release configuration in CI.
- [ ] Manually verify save → quit → relaunch → provider test on Linux.
- [x] Update README/security documentation to name the Linux Secret Service,
      Windows Credential Manager, and macOS Keychain backends and the
      memory-only degraded path.

**Acceptance evidence:** test names/output, the Linux build job, and the Linux
manual restart result are recorded in the evidence log. Windows/macOS native
backends are future-release work.
